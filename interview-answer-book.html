JavaScript core concepts

The theory questions that came up again and again: hoisting, scope, the event loop, equality, this, copying, debouncing.

Q1 What is hoisting in JavaScript?

Before your code runs, JavaScript does a quick pass over each scope and sets aside memory for every declaration it finds. That preparation step is what people call hoisting. Nothing physically moves in your file — it just means the engine already knows a name exists before the line that declares it is reached.

The catch is that the three declaration keywords get prepared differently:

Declared withName registered?Value before the declaration line
varYesundefined — usable, but meaningless
let / constYesUnusable. Touching it throws a ReferenceError
function declarationYesThe whole function — you can call it early

So a function declaration is genuinely usable before its definition, var gives you a useless undefined, and let/const protect you by throwing.

Say this in the interview

"Hoisting is the engine registering declarations in memory before execution. var is initialised to undefined, function declarations are fully available, and let/const are registered but sit in the Temporal Dead Zone until their line executes."

Q2 What happens when a let variable is hoisted? Is that the Temporal Dead Zone?

Yes. let and const are hoisted — the engine knows the name exists from the moment the block starts. But the binding has no value attached to it, and the engine deliberately refuses to let you read it. That gap between the top of the block and the declaration line is the Temporal Dead Zone (TDZ).

The proof that it really is hoisted is in the error message. If the variable weren't registered at all, you would get x is not defined. Instead you get Cannot access 'x' before initialization — the engine clearly knows about it, it just won't hand it over.

Why does this exist? It turns a silent bug into a loud one. With var, reading a variable too early quietly gives you undefined and the bug surfaces three functions later. The TDZ stops you at the exact line where the mistake is.

Q3 What is lexical scoping?

Lexical scoping means a function's access to variables is decided by where you wrote it in the source file, not by where it is called from. "Lexical" literally refers to the text of the program.

When a function looks up a variable, it checks its own scope first, then the scope it was written inside, then the one outside that, all the way up to global. That chain is fixed the moment you write the code — moving the function call somewhere else does not change it.

Follow-up they usually ask

This is exactly what makes closures possible. inner kept access to outer's variables after outer finished, because the scope chain was baked in at authoring time. A closure is just a function plus the lexical environment it remembers.

Q4 What are callbacks in JavaScript?

A callback is simply a function you hand to another function, so that the other function can call it back later. Functions are values in JavaScript, so you can pass them around like numbers or strings.

Two kinds worth separating, because interviewers like the distinction:

  • Synchronous callbacks run immediately, inside the current call — map, filter, forEach, sort.
  • Asynchronous callbacks are stored and invoked later when something finishes — timers, event listeners, network responses.

Callback hell, and why promises replaced it

When one async step depends on the previous one, callbacks nest sideways and error handling has to be repeated at every level. Promises flatten that into a chain, and async/await flattens it further into code that reads top to bottom.

Q5 Can you explain what "async" is in JavaScript?

JavaScript runs your code on a single thread. If a task takes 2 seconds and blocks that thread, the whole page freezes — no clicks, no scrolling, no rendering. Async is how JavaScript avoids that: slow work is handed off to the browser or the OS, and your function returns immediately. When the work finishes, a callback is queued and run later.

Marking a function async does two concrete things:

  • It makes the function always return a Promise, whatever you return inside it.
  • It lets you use await inside, which pauses that function only — the rest of the app keeps running.

Always handle errors

A rejected promise inside an async function behaves like a thrown exception, so try/catch works normally. Interviewers check for this.

Q6 What are microtasks and macrotasks? What goes into each queue?

When an async task finishes, its callback does not run instantly — it waits in a queue. There are two queues, and the microtask queue always wins.

The event loop's rule is strict: when the call stack empties, it drains the entire microtask queue — including any new microtasks added while draining — and only then takes one macrotask. Then it repeats.

The trap to mention

An endless stream of microtasks can starve the macrotask queue completely — the browser never gets to repaint and the tab locks up. That is why a recursive Promise.resolve().then(...) loop freezes a page, while a recursive setTimeout loop does not.

Q8 Output question: [] == false vs [] === false

Answer: true then false. You got this right in the interview — here is the exact coercion path so you can explain it confidently.

Why [] == false is true

== converts both sides until the types match. Step by step:

  1. One side is an object, the other a boolean. Booleans are converted to numbers first, so false becomes 0. Now it is [] == 0.
  2. An object compared to a number is converted to a primitive: [].toString() gives the empty string "". Now it is "" == 0.
  3. A string compared to a number becomes Number(""), which is 0. Now it is 0 == 0 → true.

Why [] === false is false

=== does no conversion at all. It compares the type first: an array is an object, false is a boolean. Different types, so it stops immediately and returns false.

The genuinely confusing part

An empty array is truthy in an if, yet it is loosely equal to false. Those are two separate rule sets — if uses Boolean(), while == uses the numeric coercion path above.

The one-liner

"Always use ===. The only reasonable exception is x == null, which conveniently catches both null and undefined in one check."

Q9 Output question: why does an arrow function method print undefined for this.name?

You answered undefined correctly, but your explanation wobbled — you said arrow functions "don't support this". Here is the precise version.

Arrow functions do not create their own this. They inherit it from the scope where they were written. And here is the key point: an object literal does not create a scope. Writing { name: "John", greet: ... } does not put you "inside" the object. So the arrow function's this comes from whatever surrounds the object — module scope or global scope — where there is no name, giving undefined.

A regular function is different: its this is decided at call time by what sits to the left of the dot. In obj.greet(), that is obj.

So when ARE arrow functions the right choice?

Exactly when you want to inherit this from outside — which is why they are perfect inside class methods, callbacks and React handlers.

Say this

"Arrow functions have no own this binding — they close over this lexically. An object literal isn't a scope, so the arrow picks up the surrounding module/global this, and this.name is undefined. Use a method shorthand when you need this to be the object."

Q10 Difference between shallow copy and deep copy

Objects and arrays are stored by reference. A variable holds a pointer, not the data. Copying decides how far down that pointer-following goes.

  • Shallow copy — new top-level container, but nested objects are still the same objects. One level deep.
  • Deep copy — everything is recreated all the way down. Completely independent.

Why this matters in React

This is the single most common cause of "my state changed but the component didn't re-render". You spread the top level, mutate something nested, and React's Object.is check sees the same nested reference — so it skips the render. Copy every level you touch.

Q12 What is debouncing? Implement a debounce function.

Debouncing delays running a function until the activity has stopped for a set period. Every new call cancels the pending one and restarts the timer. The classic use is a search box: you only want to hit the API when the user pauses typing, not on every keystroke.

"Why weren't data one and two printed?"

This was asked in your transcript. Because each call ran clearTimeout on the previous timer before it could fire. Only the final call's timer survives the 300 ms of silence. That is the whole point — intermediate keystrokes are intentionally thrown away.

And the follow-up, "will data one print if two and three are commented out?" — yes. If it is the last call, nothing cancels it.

Q14 What is a MutationObserver, and where would you use it?

A MutationObserver watches a DOM node and tells you when its children, attributes, or text change. The browser batches the changes and delivers them as an array — asynchronously, on the microtask queue — so it does not block rendering the way the old DOMSubtreeModified events did.

Honest answers for "where would you use it"

  • Third-party or legacy DOM you don't control — a payment iframe wrapper, a chat widget, or an old jQuery module injected into a React page. You cannot add a callback to their code, so you watch the DOM instead.
  • Auto-scrolling a chat or log panel when new messages are appended by something outside React.
  • Accessibility — announcing dynamically injected content to screen readers.
  • Browser extensions and analytics scripts, which by definition run on pages they didn't build.
If you haven't used it at work

Say so plainly, then show you know the boundary: "I haven't needed it in production — inside React the state is the source of truth, so watching the DOM would be working against the framework. I'd reach for it when integrating a third-party widget whose DOM I don't control." That is a stronger answer than inventing an example.

Q18 What is a linked list? What is a doubly linked list?

A linked list is a chain of nodes. Each node holds a value and a pointer to the next node. Unlike an array, the nodes are not stored side by side in memory — the pointers are what hold the sequence together.

  • Singly linked list — each node points forward only. You can only traverse in one direction.
  • Doubly linked list — each node has next and prev. You can walk both ways and delete a node in O(1) if you already hold a reference to it, at the cost of one extra pointer per node.
  • Circular — the last node points back to the head instead of null.

Access by indexO(1)O(n) — must walk from the head

Insert / delete in the middle (node known)O(n)O(1)
MemoryContiguous, cache-friendlyScattered, plus pointer overhead

Q20 Find all unique triplets in an array that sum to zero (3Sum)

The interviewer explicitly asked for brute force first, then optimisation. That is the right order — but you must be the one to say "this is O(n³), let me improve it" rather than waiting to be told.

Step 1 — brute force, O(n³)

Two things that cost you marks here

1. The missing return result. The interviewer asked about it twice. A function that builds an array and never returns it produces undefined — always trace your function to its last line before compiling.

2. "CPU time limit exceeded". That is not a broken compiler. Three nested loops over 1,000 elements is a billion iterations. The error message was the feedback: the algorithm is too slow.

Step 2 — sort + two pointers, O(n²)

Sorting first unlocks everything. Fix the first number, then walk two pointers inwards from both ends of the remaining subarray. If the sum is too small, move left right to increase it; if too big, move right left to decrease it. No hash set needed — sorted order makes duplicate-skipping trivial.

How to narrate it

"Brute force is three nested loops, O(n³), which times out past a few hundred elements. If I sort the array first — O(n log n) — I can fix the first element and use two pointers on the rest, which brings each inner search down to O(n). Total O(n²), constant extra space besides the output. Sorting also lets me skip duplicates by comparing neighbours instead of using a Set."

Q23 Why is mutating state directly dangerous in React?

React decides whether to re-render by comparing the reference of the old state to the new one (Object.is). If you mutate the existing object, the reference is unchanged, so React concludes nothing happened and skips the render — even though your data is different.

Three more consequences worth mentioning:

  • Lost updates. With batching and Concurrent features, React may render the same component twice with different state versions. Mutation makes the result depend on timing.
  • Broken optimisations. React.memo, useMemo and useEffect dependencies all rely on reference comparison. Mutation silently defeats all of them.
  • No time travel. Redux DevTools, undo/redo and optimistic-update rollback all need the previous state to still exist. Mutation destroys it.

The correct update patterns

Say this

"React uses Object.is on the state reference to decide whether to re-render. Mutating keeps the same reference, so the render is skipped and the UI goes stale. It also breaks memo, dependency arrays, and DevTools time travel. So I always produce a new object at every level I modify — or use Immer, which lets me write mutable-looking code and produces an immutable result."

Q24 A React dashboard feels slow and unresponsive. What is your first step?

The answer the interviewer wants is measure before you change anything. Never open with "I'd add useMemo" — that is guessing.

  2. React DevTools Profiler. Record the interaction. The flamegraph shows which components re-rendered, how long each took, and — most useful — why each one rendered (props changed, hooks changed, parent rendered).
  3. Chrome Performance tab. Record with 4× CPU throttling. Look for long tasks over 50 ms blocking the main thread, and layout thrashing (repeated style recalculation).

  5. Memory tab. If it degrades over time, take two heap snapshots a few minutes apart and compare. Detached DOM nodes and uncleaned subscriptions are the usual culprits.

Q25 How do you decide which parts of a dashboard to virtualize?

Virtualization means only rendering the rows currently visible in the viewport, plus a small overscan buffer. It is a real cost — you lose native Ctrl+F, you have to manage row heights, and accessibility needs care — so it should be a decision, not a default.

Four signals that make it worth it:

  • DOM node count. Roughly 1,000+ nodes in one list. A 500-row table where each row has 8 cells is already 4,000 nodes.
  • Complexity per row. Plain text rows survive a few hundred fine. Rows containing dropdowns, badges, charts or action menus start janking at 50–100.
  • Measured frame cost. If scrolling or filtering pushes render passes over 16 ms, frames are being dropped. That is the objective threshold.
  • Is pagination acceptable instead? If the product is fine with 25 rows per page, paginate — it is simpler and more accessible. Virtualize when users genuinely need to scroll a continuous dataset.

Also check fixed vs dynamic row heights. Fixed heights are trivial to virtualize. Dynamic heights (expandable rows, wrapping text) need a library that measures and caches, or you get scrollbar jumping.

Q33 <script> in the <head> versus at the end of <body>

HTML parsing is single-threaded. A plain <script> in the head blocks the parser: the browser stops building the DOM, downloads the file, executes it, and only then continues. The user stares at a blank page for the duration.

Q34 Why is the meta viewport tag needed on mobile?

Mobile browsers were built when every site was a desktop site. To avoid showing a broken 320px-wide slice of a 980px layout, they pretend the viewport is about 980 CSS pixels wide and then zoom the whole page out to fit the screen.

The result without the tag: your responsive design never triggers, because @media (max-width: 768px) is comparing against 980, not 375. The user gets a tiny, zoomed-out desktop layout and has to pinch to read anything.

  • width=device-width — make the viewport match the real device width, so media queries work against the true value.
  • initial-scale=1 — start at 100% zoom, one CSS pixel to one device-independent pixel.
Accessibility trap

Do not add user-scalable=no or maximum-scale=1. They block pinch-zoom, which fails WCAG 1.4.4 and makes the site unusable for people with low vision. iOS Safari ignores them anyway.

  3. Check for a fixed width or flex-basis that cannot shrink.
  4. Check box-sizing. Without border-box, padding is added on top of the declared width.
  5. Check for long unbroken text and add overflow-wrap: break-word.

Q39 Design a system to capture driver latitude/longitude and show live location on a dashboard

The interviewer asked you three times to "note it down in points", which means they wanted a structured flow, not prose. Use this skeleton and walk it top to bottom.

The five stages

  1. Capture — the driver's mobile app reads GPS via navigator.geolocation.watchPosition (web) or the native location service. Sample every 5–10 seconds, or on significant movement rather than on a fixed timer, to save battery.
  2. Transmit — batch a few points and send over a persistent connection (WebSocket or MQTT). Buffer locally when offline and flush on reconnect, so a tunnel doesn't create a gap in the trail.
  3. Ingest — a gateway authenticates the driver, validates the payload, and publishes to a message broker (Kafka / Kinesis). The broker decouples ingestion from processing so a slow consumer never blocks drivers.
  4. Store — two different stores for two different jobs:
    • Latest position → Redis, one key per driver, with a geospatial index. This is what the dashboard reads, and it must be fast.
    • Historical trail → a time-series or columnar store (Cassandra, TimescaleDB, S3) for replay, billing disputes and analytics.
  5. Deliver to the frontend — the dashboard subscribes to the drivers currently in its map viewport and renders markers, interpolating between updates so movement looks smooth.

The frontend side

  • Subscribe only to drivers inside the current map bounds, and resubscribe on pan/zoom. A dispatcher looking at one neighbourhood does not need all 10,000.
  • Render markers on a canvas or WebGL layer (Mapbox GL, deck.gl) rather than as DOM nodes — 1,000 DOM markers will not hold 60fps.
  • Keep marker positions in a ref, not React state. A state update per position update per driver is thousands of renders per second. Update the map layer imperatively and let React own the surrounding UI only.
  • Interpolate between the last two known points over the update interval so markers glide instead of teleporting.
  • Show the last-updated age; a stale marker that looks live is worse than one marked "no signal, 2m ago".

"Before I design, can I confirm the scale and the constraints? How many drivers, how many concurrent dashboard viewers, what update frequency do we need, and how stale can a position be before it's useless?" Interviewers score this. You jumped straight into the solution in the transcript.

Q41 Can the system handle 10,000 devices? How do you optimise for that scale?

Start by doing the arithmetic out loud — it immediately shows the problem is about volume, not about whether a technology "can handle it".

The optimisations, in order of impact

  1. Viewport-scoped subscriptions. Push only the drivers inside the client's current map bounds. This is the big one — it decouples client load from fleet size entirely.
  2. Adaptive sampling. A stationary driver needs one update a minute; one moving at 60 km/h needs one every few seconds. Send on significant change in position or heading, not on a fixed clock.
  3. Batching. One message carrying five points costs far less than five messages, in both network overhead and broker throughput.
  4. Server-side aggregation. Collect updates for 500 ms and send one combined frame per client instead of one message per driver per update.
  5. Clustering at low zoom. Zoomed out, send cluster counts ("47 drivers here"), not 47 individual coordinates. Send precise positions only as the user zooms in.
  6. Compact payloads. Drop to 5 decimal places (≈1 m precision), use short field names or a binary format like Protobuf. Roughly halves the bytes.
  7. Horizontal scaling with sharding. Partition by geographic region or by driver id hash, so each gateway node owns a slice of the fleet.

Q42 Trigger an action when a driver comes within 5 km of a location (geofencing)

The naive approach — on every update, loop over every geofence and compute the distance — is O(drivers × fences) per tick and collapses quickly. The answer is a spatial index.

Approach

  1. Index the geofences using geohashes, H3 cells, or S2. Each fence maps to the set of cells it covers.
  2. On each location update, compute the driver's cell — an O(1) hash — and look up only the fences registered in that cell and its neighbours. This turns a full scan into a handful of candidates.
  3. Precise check on those few candidates with the Haversine formula for circles, or a point-in-polygon test for arbitrary shapes.
  4. Compare with previous state. A geofence event is a transition, not a state. Store which fences the driver was inside last tick; fire ENTER only on outside→inside and EXIT only on inside→outside. Without this you fire a notification every few seconds while the driver sits inside the zone.
  5. Debounce with hysteresis. GPS jitters by tens of metres. Require two consecutive readings inside, or use a slightly larger exit radius than entry radius, so a driver parked on the boundary does not flap.
  6. Emit the event to the notification service. Do not send the push directly from the geofence worker — publish and let a dedicated service own delivery, retries and user preferences.

Q43 How do you guarantee a "package delivered" notification reaches the user, even if it's delayed?

This was the hardest follow-up in your transcript. The principle: a notification is a piece of durable state, not a fire-and-forget message. If you push and hope, an offline phone means the user never learns their package arrived.

The architecture

  1. Persist before you deliver. The event is written to a notifications table with status: pending before any push is attempted. Now it cannot be lost.
  2. Queue with retries and backoff. A worker picks it up and attempts delivery. Failures are retried with exponential backoff (1s, 5s, 30s, 2m, 10m), and after N attempts the message moves to a dead-letter queue for inspection.
  3. Multiple channels with escalation. Try push first. If there's no delivery receipt within a few minutes, fall back to SMS, then email. Users have different devices online at different times.
  4. Catch-up on reconnect. When the app comes back online it calls GET /notifications?since=<lastSeenId> and receives everything it missed. This is the safety net that makes push failure survivable — the push is an optimisation, the pull is the guarantee.
  5. Idempotency. Every notification carries a unique event id. The client deduplicates on it, so a message delivered by both push and catch-up appears once.
  6. Acknowledgement. The client confirms receipt; the server marks it delivered and stops retrying. Without an ack you cannot tell "delivered" from "silently dropped".
  7. Relevance window (TTL). A "driver is 5 minutes away" alert is useless an hour later — expire it rather than deliver it. "Package delivered" has no expiry and should always be delivered. Set the TTL per notification type.
  8. Ordering. Sequence numbers per user, so a late "out for delivery" never renders after "delivered".
The sentence that answers the question

"I treat the notification as durable state rather than a message. It's persisted with a status before any delivery attempt, retried with backoff, escalated across channels, and — most importantly — the client pulls everything it missed on reconnect using a sequence number. Push is the fast path; the catch-up query is the guarantee. Idempotency keys make double delivery harmless, and a TTL per notification type means time-sensitive alerts expire instead of arriving uselessly late."

Q45 A REST API keeps returning outdated data after an update. How do you investigate?

Work outwards layer by layer. There are five places a stale response can come from, and the browser's Network tab tells you which one within a minute.

  1. Browser cache. Hard-reload and check the Network tab. If the status says "(from disk cache)" or "(from memory cache)", it never left the machine — look at the Cache-Control response headers.
  2. Client-side state cache. TanStack Query / SWR / Redux may be serving a cached entry. Check whether the mutation invalidates the right query key.
  3. CDN or reverse proxy. Look for X-Cache: HIT, CF-Cache-Status, or an Age header greater than zero. That is a cache between you and the origin.
  4. Application-level cache. Redis or in-process memoisation on the server that the write path never invalidated.
  5. Database replication lag. Writes go to the primary, reads go to a replica that hasn't caught up. Test by reading from the primary directly — if that returns fresh data, it is replication.

The fastest diagnostic: call the endpoint with curl, bypassing the browser entirely. Fresh data means the problem is client-side. Stale data means it is server-side, and the response headers narrow it further.

The fixes

  • CDN: purge the path on deploy or on write, and make sure your cache key includes anything that varies the response (auth, locale, query params).
  • Redis: delete or update the key in the same transaction as the write, not in a separate step that can fail independently.
  • Replication lag: route reads to the primary for a short window after a write ("read your own writes"), or pass the write's LSN so the replica waits.
Say this

"I'd bisect the layers rather than guess. First curl the endpoint to rule the browser in or out, then read the response headers — Age, X-Cache and Cache-Control tell you immediately whether a CDN is serving it. If the origin itself is stale, I'd check the app cache invalidation on the write path, and finally test a read against the primary to rule out replica lag."

Q53 How would you migrate a legacy ES5 codebase with prototype chains and dynamic properties to ES6+?

The instinct to resist is "rewrite it". Say the opposite: a staged, reversible migration where the app works at every commit.

  1. Get a safety net first. You cannot safely refactor untested code. Add characterisation tests around the riskiest modules — tests that capture current behaviour, bugs included, so you can tell whether you changed anything.
  2. Set up the build to accept both. Babel plus a bundler, so ES6 modules and ES5 scripts coexist. Nothing else can start until this works.
  3. Automate the mechanical parts. var→let/const, string concatenation → template literals, callbacks → promises. Tools like lebab and codemods handle these, and mechanical changes should not consume human review time.
  4. Module system next. IIFEs and globals → ES modules. This is the change that unlocks tree-shaking, bundle splitting and static analysis, so it pays for itself fastest.
  5. Prototype chains → classes, one hierarchy at a time. class is mostly syntax over prototypes, so the conversion is usually safe — but watch for code that reassigns prototype at runtime or relies on calling a constructor without new. Classes throw in that case.
  6. Dynamic property assignment is the genuinely hard part. Objects built by obj[key] = value at runtime have no static shape. Keep them as plain objects or Maps, and if you later add TypeScript, model them with index signatures rather than pretending they have fixed keys.
  7. TypeScript last, in allowJs mode. Rename files to .ts one at a time, start with strict: false, and tighten the compiler settings gradually.
The line that shows seniority

"Every commit ships. If the migration stalls halfway — which happens, because priorities change — the codebase should be in a better state than when I started, not a worse one. That rules out a parallel rewrite branch."

Q54 How do you handle disagreement with a designer about breakpoints or layout, under deadline?

Answer this as a collaboration question, because that is what it is. The failure modes they are screening for are "I just build whatever the design says" and "I overrode it because it wasn't technically sensible".

  1. Understand the intent first. "What's the priority on this screen at mobile width?" A designer who wants the CTA visible without scrolling has a goal, not a pixel preference — and there are usually several ways to hit it.
  2. Bring data, not opinion. "42% of our traffic is 390px wide, and at that width this table needs horizontal scroll" ends an argument that "it'll be cramped" would not.
  3. Prototype instead of debating. Twenty minutes building both versions in a branch settles it faster than an hour in a meeting. Preview deployments per PR exist for this.
  4. Name the actual cost. "That version is two days; this one is four hours and 90% of the effect. With the deadline on Friday, which do you want?" That is a trade-off you present, not a decision you make alone.
  5. Escalate to the goal, not up the org chart. If you genuinely cannot agree, bring in the PM to weigh it against the release, and be willing to lose.
  6. Prevent it recurring with a shared design system: agreed breakpoints, spacing scale and component states, so these debates happen once rather than per feature.
Good closing line

"I try to disagree about the goal rather than the pixels. Most of these turn out to be the designer and me optimising for different things, and once that's on the table the solution is usually obvious to both of us."

Q55 How do you optimise a heavy dashboard for low-end mobile devices, and what do you degrade?

Measure on the real thing first

Test with 4× CPU throttling and Slow 4G, or better, a real budget Android device. A dashboard that feels fine on a MacBook can take 12 seconds to become interactive on a phone with a 5-year-old chipset.

Load performance

  • Route-level code splitting — ship only what the current screen needs.
  • Audit the bundle with source-map-explorer. Moment.js, full lodash, a whole charting library for one sparkline, and duplicated dependencies are the usual findings.
  • Modern image formats (AVIF/WebP) with srcset, and loading="lazy" below the fold.
  • Self-host fonts, subset them, and use font-display: swap.
  • Server-render or statically generate the shell so something meaningful paints before the JS lands.

Runtime performance

  • Virtualize long lists (Q25).
  • Animate only transform and opacity — they run on the compositor and skip layout entirely.
  • Move heavy computation to a Web Worker.
  • Use content-visibility: auto on off-screen sections so the browser skips rendering them.

What to degrade — and how to decide

The rule: protect the core job, degrade the enhancements. On a delivery dashboard the core job is "see where my orders are". Everything else is negotiable.

FeatureLow-end treatment
Live-updating chartsStatic snapshot with a "refresh" button
Real-time WebSocket feedPolling every 30s — far less battery and CPU
Animated transitionsOff. Also honours prefers-reduced-motion for free
Map with 500 live markersClustered markers, or a list view
Auto-refresh every 5sManual pull-to-refresh
High-res imageryLower-resolution variants via srcset
The framing that scores

"I'd separate the core user job from enhancements, and make sure the core path works on the worst device we support. Then I'd degrade enhancements based on actual signals — hardwareConcurrency, deviceMemory, connection.effectiveType, saveData — rather than user-agent sniffing. And I'd give the user the choice too: a 'lite mode' toggle respects that they know their situation better than my heuristic does."

Q56 "Keep your answers shorter and to the point"

This feedback appeared explicitly in one transcript, and the pattern shows up across several: long answers that circle back, restate, and trail off without a conclusion.

A structure that fixes it

  1. Lead with the answer. One sentence. "I'd profile before changing anything." Then elaborate. Interviewers are scoring whether you know the answer, and they hear it in the first sentence or they start doubting.
  2. Give 2–4 supporting points, not eight. Depth beats coverage.
  3. Stop, and hand it back. "That's my approach — happy to go deeper on any part." This turns a monologue into a conversation and lets them steer to what they care about.

Specific habits from your transcripts

  • Think out loud, but announce it. "Let me think through this for a moment" is fine. Long stretches of half-sentences read as not knowing.
  • Say when you don't know, then say what you'd do. "I haven't implemented that, but my approach would be…" is a complete, strong answer. Bluffing into vagueness is the weakest option available.
  • Read your code before compiling. Two of your rounds were lost to lenght and a missing return. Thirty seconds of reading top to bottom would have saved twenty minutes of prompting.
  • Narrate the plan before you type. "Two pointers from both ends; on mismatch I'll try skipping each side." If you then make a typo, the interviewer already knows your logic was right.
  • Ask clarifying questions in system design. Scale, constraints, and who the users are. You went straight to solutions in the transcripts; the question itself earns marks.
  • Own the boundary of your experience early. "I owned the frontend, so I'll describe the backend at the level I worked against it" is much stronger said up front than admitted under follow-up.
