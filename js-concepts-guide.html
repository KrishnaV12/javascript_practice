01
Scope
Global · Function · Block
Theory

Scope defines the accessibility (visibility) of variables. JavaScript has three kinds:

Global Scope — Variables declared outside any function/block are accessible everywhere in the script.

Function Scope — Variables declared inside a function are only accessible within that function. Each function call creates a new scope.

Block Scope — Introduced with ES6. Variables declared with let/const inside {} (if, for, while) are scoped to that block.

⚡ var ignores block scope — it leaks out of if/for blocks into the enclosing function. This is a classic JS footgun.
⚛In React, component function bodies create function scope. State, refs, and memoized values all live in this scope. Hooks must be called at the top level of this scope.
scope.js
// ── GLOBAL SCOPE ──────────────────────────────
const appName = "MyApp";  // accessible everywhere

// ── FUNCTION SCOPE ────────────────────────────
function greet() {
  const message = "Hello!";  // only inside greet()
  console.log(message);       // ✅ works
}
console.log(message);         // ❌ ReferenceError

// ── BLOCK SCOPE ───────────────────────────────
if (true) {
  let   blockLet   = "block only";
  const blockConst = "block only";
  var   blockVar   = "leaks out!";
}
console.log(blockVar);       // ✅ "leaks out!"
console.log(blockLet);       // ❌ ReferenceError

// ── REACT EXAMPLE ─────────────────────────────
function UserCard({ userId }) {
  // userId is in UserCard's function scope
  const [user, setUser] = useState(null);

  useEffect(() => {
    // closure over userId in this block scope
    if (userId) {
      const url = `/api/user/${userId}`;
      fetchUser(url).then(setUser);
    }
  }, [userId]);
}
02
Scope Chaining
Lexical Environment
Theory

When JS looks up a variable, it starts in the current scope and walks up the chain of parent scopes until it finds it or reaches global. This is the scope chain.

Each scope has a reference to its outer lexical environment — the scope where the code was written, not where it runs. This is "lexical scoping."

The scope chain is determined at author time, not at runtime. Nested functions always have access to their parent's variables.
⚛Custom hooks rely on lexical scope — when a hook like useForm() returns helpers, they close over internal state through the lexical environment of the hook's function body.
scope-chain.js
const global = "🌍 global";

function outer() {
  const outerVar = "outer";

  function middle() {
    const middleVar = "middle";

    function inner() {
      // Scope chain lookup: inner → middle → outer → global
      console.log(global);     // ✅ "🌍 global"
      console.log(outerVar);   // ✅ "outer"
      console.log(middleVar);  // ✅ "middle"
    }
    inner();
  }
  middle();
}
outer();

// ── LEXICAL ENV in React Custom Hook ──────────
function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);

  // These functions close over setCount via scope chain
  const increment = () => setCount(c => c + 1);
  const decrement = () => setCount(c => c - 1);
  const reset     = () => setCount(initial);

  return { count, increment, decrement, reset };
}

⚛In React: always use const for component declarations, hooks, and event handlers. Use let only for loop counters or mutable accumulators. Never use var in modern React code.

// ── var: function-scoped, hoisted ─────────────
function varDemo() {
  console.log(x);   // undefined (hoisted)
  var x = 5;

  console.log(x);   // 5 ✅
}

// user = {}          // ❌ TypeError: reassignment

const Button = ({ onClick, label }) => {
  const handleClick = () => {
    onClick();
  };

};
04
Temporal Dead Zone
TDZ
Theory

The Temporal Dead Zone (TDZ) is the period from the start of a block scope until a let/const variable is declared and initialized.

During the TDZ, the variable exists in memory (hoisted) but is in an uninitialized state. Any access throws a ReferenceError.

The TDZ exists to prevent you from using a variable before it's ready — a safety net that var never provided.
⚛TDZ mostly matters when debugging — if you see "Cannot access 'X' before initialization" in React, a hook or variable is being used before its declaration in the render flow.
tdz.js
// ── TDZ with let ──────────────────────────────
{
  // TDZ starts here for `name`
  console.log(name);  // ❌ ReferenceError: TDZ!
  let name = "Alice";  // TDZ ends here
  console.log(name);  // ✅ "Alice"
}

// ── var has NO TDZ ────────────────────────────
{
  console.log(age);   // undefined (no error)
  var age = 30;
}

// ── TDZ in class fields ───────────────────────
class Config {
  size = this.count * 2;  // ❌ TDZ: count not yet set
  count = 10;
}

// ── Common React TDZ trap ─────────────────────
function Component() {
  // ❌ Can't use `data` here — TDZ
  useEffect(() => {
    console.log(data);  // ✅ OK — closure captures after init
  }, []);

  const data = useFetchData();  // declared below useEffect
  return null;
}
05
Hoisting
Theory

Hoisting is JS's behavior of moving declarations to the top of their scope during the compilation phase (before execution).

Function declarations are fully hoisted — you can call them before they appear in code.
var declarations are hoisted but initialized to undefined.
let/const are hoisted but stay in the TDZ until their declaration line.

Classes are also hoisted but remain in TDZ — you can't use a class before its declaration.
⚛React function components benefit from hoisting — you can call a helper function before its definition in the file, though this is a style choice. Hooks (function expressions) are NOT hoisted the same way.
hoisting.js
// ── Function Declaration: fully hoisted ───────
sayHello();  // ✅ "Hello!" — works before declaration
function sayHello() { console.log("Hello!"); }

// ── Function Expression: NOT hoisted ──────────
greet();  // ❌ TypeError: greet is not a function
var greet = function() { console.log("Hi"); };

// ── What JS actually does (mentally) ──────────
// var greet = undefined  ← hoisted declaration
// greet()               ← calling undefined()

// ── var hoisting ──────────────────────────────
function example() {
  console.log(a);  // undefined (not ReferenceError)
  console.log(b);  // ❌ ReferenceError (TDZ)
  var a = 1;
  let b = 2;
}

// ── React: class components & hoisting ────────
// ❌ This fails — class is in TDZ
const elem = new MyComponent();
class MyComponent extends React.Component {}

// ✅ Always define classes/components before use
06
Closures
Theory

A closure is a function that remembers its lexical scope even when executed outside of it. The inner function retains access to the outer function's variables even after the outer function has returned.

Closures enable: data encapsulation, factory functions, memoization, and partial application.

🔑 Every React hook is built on closures. useState, useEffect, useCallback — they all capture variables from the component's render scope via closures.
⚠️ Stale closure bug: when a closure captures an old value of state/props and doesn't update. Always specify the correct dependency array in hooks.
⚛The infamous "stale closure" in useEffect happens when the effect captures a value once and never re-captures the updated value. Fix: include the value in the dep array or use a ref.
closures.js
// ── Basic Closure ─────────────────────────────
function makeCounter() {
  let count = 0;  // private via closure

  return {
    increment: () => ++count,
    decrement: () => --count,
    value:     () => count,
  };
}
const counter = makeCounter();
counter.increment();  // 1
counter.increment();  // 2
counter.value();     // 2

// ── Stale Closure Bug in React ────────────────
function Timer() {
  const [count, setCount] = useState(0);

  // ❌ Stale closure — count is always 0
  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);  // always 0!
    }, 1000);
    return () => clearInterval(id);
  }, []);  // ← empty deps = stale closure

  // ✅ Fix 1: add count to deps
  useEffect(() => {
    const id = setInterval(() => {
      setCount(c => c + 1);  // functional update
    }, 1000);
    return () => clearInterval(id);
  }, []);
}
07
Prototype & Prototype Chaining
Theory

Every JS object has an internal [[Prototype]] link (accessible via __proto__ or Object.getPrototypeOf). When you access a property, JS first looks on the object itself, then walks up the prototype chain until it finds the property or hits null.

Classes in ES6 are syntactic sugar over prototype-based inheritance. Under the hood, class extends sets up the prototype chain.

Methods on a prototype are shared across all instances — they're not copied per object. This is memory-efficient.
⚛React class components use prototype inheritance (extends React.Component). Functional components don't — but knowing prototypes helps debug class component issues and understand how React.Component's lifecycle methods work.
prototype.js
// ── Prototype Chain ───────────────────────────
function Animal(name) {
  this.name = name;
}
Animal.prototype.speak = function() {
  return `${this.name} makes a sound.`;
};

function Dog(name) {
  Animal.call(this, name);  // inherit properties
}
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.bark = function() {
  return "Woof!";
};

const dog = new Dog("Rex");
// Lookup: dog → Dog.prototype → Animal.prototype → Object.prototype → null
dog.bark();   // "Woof!" — own method
dog.speak();  // "Rex makes a sound." — up chain

// ── ES6 Class (same under the hood) ───────────
class Cat extends Animal {
  meow() { return "Meow!"; }
}
Object.getPrototypeOf(Cat.prototype)
  === Animal.prototype;  // true
08
Call, Apply & Bind
Theory

These three methods let you explicitly set the value of this when calling a function:

call(thisArg, ...args) — invokes immediately, args passed individually.

apply(thisArg, [args]) — invokes immediately, args as an array.

bind(thisArg, ...args) — returns a new function with this bound, doesn't invoke immediately.

Memory trick: Call = Comma separated args, Apply = Array, Bind = returns a bound copy.
⚛Arrow functions in React components don't have their own this — they inherit from the enclosing scope. This is why we prefer arrow functions for event handlers in class components. In functional components, this is largely irrelevant.
call-apply-bind.js
const user = { name: "Alice", age: 30 };

function introduce(greeting, punctuation) {
  return `${greeting}, I'm ${this.name}${punctuation}`;
}

// ── call ──────────────────────────────────────
introduce.call(user, "Hi", "!");
// "Hi, I'm Alice!"

// ── apply ─────────────────────────────────────
introduce.apply(user, ["Hello", "."]);
// "Hello, I'm Alice."

// ── bind ──────────────────────────────────────
const aliceIntro = introduce.bind(user, "Hey");
aliceIntro("~");  // "Hey, I'm Alice~"

// ── Practical: borrowing methods ──────────────
const arrayLike = { 0: "a", 1: "b", length: 2 };
const arr = Array.prototype.slice.call(arrayLike);
// ["a", "b"]

// ── React Class Component (historical) ────────
class Toggle extends React.Component {
  constructor(props) {
    super(props);
    this.state = { on: false };
    // bind needed for regular methods
    this.handleClick = this.handleClick.bind(this);
  }
  handleClick() {
    this.setState(s => ({ on: !s.on }));
  }
}
09
Pass by Value vs Pass by Reference
Theory

Primitives (string, number, boolean, null, undefined, Symbol, BigInt) are passed by value — a copy of the data is made.

Objects & Arrays are passed by reference — the variable holds a reference to the same memory location. Mutations inside a function affect the original.

⚠️ JS is technically "pass by value of the reference" — you can mutate an object's properties, but you can't reassign the variable to point to a new object from inside a function.
⚛This is why React state must be immutably updated — mutating state directly won't trigger re-renders because React's shallow equality check sees the same reference. Always spread or use Immer for state updates.
pass-by-value-ref.js
// ── Primitives: by VALUE ──────────────────────
let a = 5;
let b = a;    // b gets a COPY of 5
b = 10;
console.log(a);  // 5 — unchanged

// ── Objects: by REFERENCE ─────────────────────
const obj1 = { count: 1 };
const obj2 = obj1;    // same reference
obj2.count = 99;
console.log(obj1.count);  // 99 😱 mutated!

// ── React: WHY immutability matters ───────────
const [items, setItems] = useState([1, 2, 3]);

// ❌ WRONG — mutates existing array, same reference
const addItem = () => {
  items.push(4);       // React won't re-render!
  setItems(items);     // same ref = no update
};

// ✅ CORRECT — new array reference
const addItemCorrect = () => {
  setItems([...items, 4]);  // new reference ✅
};

// ✅ CORRECT — deep object update
const updateUser = () => {
  setUser(prev => ({ ...prev, name: "Bob" }));
};
10
Currying in JavaScript
Theory

Currying transforms a function that takes multiple arguments into a sequence of functions each taking a single argument: f(a, b, c) → f(a)(b)(c)

It enables partial application — creating specialized functions from general ones by pre-filling some arguments.

Currying is a FP (Functional Programming) pattern that promotes reusability and composability. It's the core of libraries like Ramda and lodash/fp.
⚛Common in React for event handler factories: const handleChange = (field) => (e) => setForm(p => ({...p, [field]: e.target.value})) — one curried function handles all form fields.
currying.js
// ── Basic Currying ────────────────────────────
const add = (a) => (b) => a + b;
add(2)(3);         // 5
const add5 = add(5);  // partial application
add5(10);           // 15

// ── Generic curry utility ─────────────────────
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn.apply(this, args);
    }
    return (...more) => curried(...args, ...more);
  };
}

const multiply = curry((a, b, c) => a * b * c);
multiply(2)(3)(4);    // 24
multiply(2, 3)(4);   // 24
multiply(2, 3, 4);  // 24

// ── React: Curried Event Handler ──────────────
function LoginForm() {
  const [form, setForm] = useState({email:"",pass:""});

  // One curried function for all fields!
  const handleChange = (field) => (e) =>
    setForm(p => ({ ...p, [field]: e.target.value }));

  return (
    <>
      <input onChange={handleChange("email")} />
      <input onChange={handleChange("pass")}  />
    </>
  );
}
11
Memoization
Theory

Memoization is an optimization that caches a function's results for given inputs so the same computation isn't repeated. It's a form of trading memory for speed.

A memoized function stores previous results in a cache (usually a Map or object). When called with the same arguments, it returns the cached result instead of recomputing.

Best for: expensive pure functions (no side effects) called frequently with the same inputs. Don't memoize everything — the cache overhead can cost more than the saved computation.
⚛React has three built-in memoization tools: useMemo (memoize computed values), useCallback (memoize functions), and React.memo (memoize component renders). Use them when you have a measured performance problem, not preemptively.
memoization.js
// ── Manual Memoize ────────────────────────────
function memoize(fn) {
  const cache = new Map();
  return function(...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

// Fibonacci without memoization: O(2^n)
const fib = memoize(function(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
});
fib(40);  // instant with cache; without: millions of calls

// ── React useMemo ─────────────────────────────
function ProductList({ products, search }) {
  // Only recomputes when products or search changes
  const filtered = useMemo(
    () => products.filter(p =>
      p.name.toLowerCase().includes(search.toLowerCase())),
    [products, search]
  );

  // useCallback: memoize function reference
  const handleSelect = useCallback((id) => {
    selectProduct(id);
  }, []);

  return filtered.map(p =>
    <ProductItem key={p.id} onSelect={handleSelect} />
  );
}
12
Event Loop
Theory

JavaScript is single-threaded but non-blocking thanks to the event loop. The runtime has:

Call Stack — where synchronous code executes (LIFO). Only one thing runs at a time.

Web APIs — browser provides async capabilities (setTimeout, fetch, DOM events). These run off the main thread.

Task Queue (Macrotask) — setTimeout, setInterval, I/O callbacks wait here.

Microtask Queue — Promise callbacks, queueMicrotask, MutationObserver. Always drained before the next task.

🔑 Order: Synchronous → Microtasks (all of them) → Next Macrotask → Microtasks → Next Macrotask...
⚛React's useState batches updates within the same event handler. In React 18, updates from setTimeout/Promises are also auto-batched. Understanding the event loop explains why setState is asynchronous and why you see stale values immediately after calling it.
event-loop.js
console.log("1 - sync");

setTimeout(() => console.log("4 - macrotask"), 0);

Promise.resolve().then(() => console.log("3 - microtask"));

console.log("2 - sync");

// Output: 1, 2, 3, 4
// Sync → Microtask → Macrotask

// ── Tricky nested example ─────────────────────
setTimeout(() => {
  console.log("timeout");
  Promise.resolve().then(() =>
    console.log("promise inside timeout"));
}, 0);
// Output: "timeout" → "promise inside timeout"
// Microtask runs before the NEXT macrotask

// ── React 18 Auto-batching ────────────────────
function handleClick() {
  // React 18: both updates batched = 1 re-render
  setTimeout(() => {
    setCount(c => c + 1);  // batched ✅
    setFlag(true);           // batched ✅
  });
}
13
Callback Queue vs Microtask Queue
Theory

Macrotask Queue (Task Queue / Callback Queue): setTimeout, setInterval, setImmediate, I/O, UI events. The event loop picks one macrotask per cycle.

Microtask Queue: Promise .then/.catch/.finally, async/await continuations, queueMicrotask(), MutationObserver. The event loop drains all microtasks after each macrotask (or at end of sync code).

Microtasks are processed until the queue is empty before moving to the next macrotask. An infinite microtask loop would freeze the browser!
⚛flushSync in React forces synchronous re-renders. startTransition defers updates as "non-urgent" (processed in later render cycles). Understanding these queues explains React 18's concurrent rendering model.
queues.js
// ── Queue Priority Demo ───────────────────────
console.log("[1] Script start");

setTimeout(() => console.log("[5] setTimeout"), 0);

Promise.resolve()
  .then(() => console.log("[3] Promise 1"))
  .then(() => console.log("[4] Promise 2"));

queueMicrotask(() => console.log("[3b] queueMicrotask"));

console.log("[2] Script end");

// Output order: 1 → 2 → 3 → 3b → 4 → 5

// ── What queue is what ────────────────────────
// Macrotasks:  setTimeout, setInterval, fetch CB
// Microtasks:  .then, async/await, queueMicrotask

// ── React startTransition (defer = macrotask-ish)
import { startTransition } from "react";

function handleSearch(e) {
  // Urgent: update the input immediately
  setQuery(e.target.value);

  // Non-urgent: defer heavy list filtering
  startTransition(() => {
    setSearchResults(filterItems(e.target.value));
  });
}
14
Promises
Theory

A Promise is an object representing an eventual value — it can be in one of three states: pending, fulfilled, or rejected.

Promises solve "callback hell" by providing chainable .then() and .catch() methods. Once settled, a promise's state never changes.

Promise.all Promise.allSettled Promise.race Promise.any
Promise.all — fails fast on first rejection
Promise.allSettled — waits for all, reports each outcome
Promise.race — resolves/rejects with first to settle
Promise.any — resolves with first success
⚛React Query / SWR are built on top of Promises. When you write data-fetching hooks, understanding Promise chaining and error propagation helps debug loading/error states correctly.
promises.js
// ── Creating a Promise ────────────────────────
const fetchUser = (id) => new Promise((resolve, reject) => {
  setTimeout(() => {
    if (id > 0) resolve({ id, name: "Alice" });
    else        reject(new Error("Invalid ID"));
  }, 500);
});

// ── Chaining ──────────────────────────────────
fetchUser(1)
  .then(user => user.name.toUpperCase())
  .then(name => console.log(name))   // "ALICE"
  .catch(err => console.error(err))
  .finally(() => setLoading(false));

// ── Promise.all — parallel fetch ──────────────
const loadDashboard = async () => {
  const [user, posts, stats] = await Promise.all([
    fetch("/api/user").then(r => r.json()),
    fetch("/api/posts").then(r => r.json()),
    fetch("/api/stats").then(r => r.json()),
  ]);
  return { user, posts, stats };
};
15
Async / Await
Theory

async/await is syntactic sugar over Promises. An async function always returns a Promise. await pauses execution inside the async function until the Promise settles — without blocking the main thread.

Under the hood, each await suspends the function and schedules the rest as a microtask on the promise chain.

⚠️ Sequential awaits can be slow: await a(); await b(); runs in series. Use Promise.all([a(), b()]) for parallel execution.
⚛In useEffect, you can't make the callback itself async — async functions return promises and React would need to clean up the promise. Instead, declare an inner async function and call it. React 19's use() hook is changing this pattern.
async-await.js
// ── Basic async/await ─────────────────────────
async function getUser(id) {
  try {
    const res  = await fetch(`/api/user/${id}`);
    if (!res.ok) throw new Error("Not found");
    const data = await res.json();
    return data;
  } catch (err) {
    console.error(err);
  }
}

// ── Sequential vs Parallel ────────────────────
// ❌ Sequential: waits for each
const a = await fetchA();  // 300ms
const b = await fetchB();  // 200ms = total 500ms

// ✅ Parallel: runs simultaneously
const [a, b] = await Promise.all([fetchA(), fetchB()]);
// total: 300ms (max of both)

// ── React useEffect + async ───────────────────
useEffect(() => {
  let cancelled = false;

  async function load() {
    const data = await fetchUser(userId);
    if (!cancelled) setUser(data);  // race condition guard
  }

  load();
  return () => { cancelled = true; };  // cleanup
}, [userId]);
16
Event Bubbling & Capturing
Theory

DOM events propagate in three phases:

1. Capture Phase — event travels down from window → target element. (useCapture = true)

2. Target Phase — event reaches the target element.

3. Bubble Phase — event bubbles up from target → window. (default)

Use e.stopPropagation() to stop bubbling. Use e.preventDefault() to prevent default browser behavior.

Most event listeners use the bubble phase. Use capture only for special needs (e.g., intercepting events before they reach the target).
⚛React uses synthetic events and attaches a single listener at the root. React 17+ changed from document-level to root-level delegation. e.stopPropagation() still works within React's synthetic event system, but won't stop native DOM events from propagating.
bubbling-capturing.js
// ── Event Bubbling ────────────────────────────
// HTML: <div id="outer"><div id="inner"></div></div>

outer.addEventListener("click", () =>
  console.log("Outer (bubble)"));

inner.addEventListener("click", () =>
  console.log("Inner (bubble)"));

// Click inner: "Inner" → "Outer" (bubbles up)

// ── Capturing ─────────────────────────────────
outer.addEventListener("click",
  () => console.log("Outer (capture)"),
  true  // useCapture flag
);
// Click inner: "Outer (capture)" → "Inner (bubble)"

// ── stopPropagation ───────────────────────────
inner.addEventListener("click", (e) => {
  e.stopPropagation();
  console.log("Only inner fires");
});

// ── React: Stopping Propagation ───────────────
function Modal({ onClose }) {
  return (
    <div className="overlay" onClick={onClose}>
      <div
        className="modal-content"
        onClick={e => e.stopPropagation()}
      >
        {/* clicks here won't close the modal */}
      </div>
    </div>
  );
}
17
Event Delegation
Theory

Event Delegation leverages bubbling to attach a single event listener to a parent element instead of multiple listeners to each child. The event bubbles up and you identify the target using event.target.

Benefits: memory efficiency (one listener vs. hundreds), works for dynamically added elements.

This is exactly what React does internally! React 17+ attaches all event listeners to the React root container, not to individual DOM nodes — the ultimate event delegation.
⚛While React handles this automatically, you'll use manual event delegation when integrating vanilla JS libraries into React, or when optimizing large lists that React.memo can't fully address.
event-delegation.js
// ── WITHOUT delegation: 1000 listeners ────────
document.querySelectorAll(".item").forEach(el => {
  el.addEventListener("click", handleClick);  // 😱
});

// ── WITH delegation: 1 listener ───────────────
document.querySelector("#list").addEventListener(
  "click",
  (e) => {
    const item = e.target.closest("[data-id]");
    if (item) handleClick(item.dataset.id);
  }
);

// ── React version (delegation is automatic) ───
function TodoList({ todos }) {
  // React delegates all onClick to root internally
  const handleClick = (id) => toggleTodo(id);

  return (
    <ul>
      {todos.map(t => (
        <li key={t.id}
            onClick={() => handleClick(t.id)}>
          {t.text}
        </li>
      ))}
    </ul>
  );
}

Debounce
Theory

Debounce delays the execution of a function until a specified time has passed since the last call. If the function is called again within the delay, the timer resets.

Use case: search inputs — wait until the user stops typing before firing the API call.

Debounce = "Call only after things quiet down." Each new call pushes the timer back.
⚛Wrap debounced functions in useCallback to preserve the reference. Or use a library like use-debounce. The debounce timer lives inside a closure — this is closures + timers working together.
debounce.js
// ── Debounce Implementation ───────────────────
function debounce(fn, delay) {
  let timer;
  return function(...args) {
    clearTimeout(timer);             // reset timer
    timer = setTimeout(() => {
      fn.apply(this, args);
    }, delay);
  };
}

// Usage
const debouncedSearch = debounce((query) => {
  searchAPI(query);
}, 300);

// Fires 300ms after user stops typing
input.addEventListener("input", (e) =>
  debouncedSearch(e.target.value));

// ── React Hook ────────────────────────────────
function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() =>
      setDebounced(value), delay
    );
    return () => clearTimeout(timer);
  }, [value, delay]);

  return debounced;
}

// Usage in component:
const debouncedQuery = useDebounce(query, 300);
useEffect(() => { fetchResults(debouncedQuery); },
  [debouncedQuery]);

Throttle
Theory

Throttle ensures a function executes at most once per time interval, regardless of how many times it's triggered. Unlike debounce, it guarantees regular execution during sustained activity.

Use case: scroll handlers, resize handlers, mouse move — events that fire rapidly where you want periodic updates.

Throttle = "Execute at a maximum rate." Debounce waits for quiet. Throttle runs regularly during activity.
⚛For scroll-based React animations or lazy-loading, throttle is your friend. Combine with useRef to store the throttle state without causing re-renders.
throttle.js
// ── Throttle Implementation ───────────────────
function throttle(fn, limit) {
  let inThrottle = false;
  return function(...args) {
    if (!inThrottle) {
      fn.apply(this, args);
      inThrottle = true;
      setTimeout(() => {
        inThrottle = false;
      }, limit);
    }
  };
}

// Fires at most once per 100ms during scroll
const throttledScroll = throttle(() => {
  updateScrollPosition();
}, 100);
window.addEventListener("scroll", throttledScroll);

// ── React: Scroll Position Hook ───────────────
function useScrollPosition() {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  const ticking = useRef(false);

  useEffect(() => {
    const handler = () => {
      if (!ticking.current) {
        requestAnimationFrame(() => {
          setPos({ x: window.scrollX, y: window.scrollY });
          ticking.current = false;
        });
        ticking.current = true;
      }
    };
    window.addEventListener("scroll", handler);
    return () => window.removeEventListener("scroll", handler);
  }, []);

  return pos;
}

JavaScript Execution Context
How JS Parses & Executes Code
Theory

An Execution Context (EC) is the environment in which JS code is evaluated. Every EC has:

Variable Environment — storage for var declarations, function declarations.

Lexical Environment — storage for let/const, reference to outer scope.

this binding — the value of this within this context.

EC creation happens in two phases: Creation Phase (memory allocation, hoisting) and Execution Phase (code runs line by line).

The Global EC is created first. Each function call creates a new EC pushed onto the Call Stack. When a function returns, its EC is popped.
⚛Every React render call creates a new execution context for the component function. This is why every render gets fresh closures over props/state — a new EC means new lexical environments for all the hook calls.
execution-context.js
// ══ PHASE 1: Creation Phase ════════════════════
// JS engine scans code and allocates memory:
// - var declarations → undefined
// - function declarations → full definition
// - let/const → TDZ (uninitialized)

// ══ PHASE 2: Execution Phase ═══════════════════
// Code executes line by line

// Execution stack trace:
// Global EC → multiply EC → add EC

var num = 10;            // Global EC

function multiply(a, b) {  // new EC created
  function add(x, y) {  // another new EC
    return x + y;
  }                      // add EC popped
  return add(a, 0) * b;
}                        // multiply EC popped

multiply(5, 2);

// ── Call Stack Visualization ──────────────────
// │ add EC        │ ← top of stack (executing)
// │ multiply EC   │
// │ Global EC     │ ← bottom (always present)
// └───────────────┘

// ── React: Each render = new EC ───────────────
function Counter() {
  // New EC created for each render:
  // • fresh `count` closure
  // • fresh `setCount` reference
  // • fresh event handlers
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c+1)}>{count}</button>;
}

Theory

This is the foundation of all higher-order patterns, closures, callbacks, and functional programming in JS.
⚛React components ARE first-class functions. You pass them as props, store them in arrays, conditionally render them. <Component /> is syntactic sugar for React.createElement(Component, ...) — just a function call.

Higher Order Functions
Theory

A Higher Order Function (HOF) is a function that either takes a function as an argument or returns a function (or both). Built on first-class functions.

Built-in HOFs: Array.map, Array.filter, Array.reduce, Array.forEach, Array.sort.

⚛HOFs are everywhere in React: React.memo(Component), HOC (Higher Order Components) like withAuth(Component), connect() from Redux — all take a component and return a new component.
hof.js
// ── Built-in HOFs ─────────────────────────────
const nums = [1, 2, 3, 4, 5];
nums.map(x => x * 2);           // [2,4,6,8,10]
nums.filter(x => x % 2 === 0);  // [2, 4]
nums.reduce((acc,x) => acc+x, 0); // 15

// ── Custom HOF ────────────────────────────────
function withLogging(fn) {
  return function(...args) {
    console.log(`Calling ${fn.name} with`, args);
    const result = fn(...args);
    console.log(`Result:`, result);
    return result;
  };
}
const loggedAdd = withLogging((a,b) => a+b);

// ── React HOC Pattern ─────────────────────────
function withAuth(WrappedComponent) {
  return function AuthGuard(props) {
    const isAuth = useAuth();
    if (!isAuth) return <Redirect to="/login" />;
    return <WrappedComponent {...props} />;
  };
}

Variable Shadowing
Theory

Variable Shadowing occurs when an inner scope declares a variable with the same name as a variable in an outer scope. The inner declaration "shadows" (hides) the outer one within its scope.

let/const can shadow outer let/const or var. However, var cannot shadow another var in the same function (it just overwrites).

⚠️ Accidental shadowing is a common source of bugs. ESLint's no-shadow rule prevents this in teams.
⚛Shadowing is common in React when using generic names like data, error, isLoading in nested hooks. Use descriptive names to avoid confusion: userData, postsData.
shadowing.js
let message = "outer";

function outer() {
  console.log(message);  // "outer"

  if (true) {
    let message = "inner";  // shadows outer
    console.log(message);    // "inner"
  }

  console.log(message);  // "outer" (restored)
}

// ── Illegal shadowing ─────────────────────────
let a = 1;
{
  var a = 2;  // ❌ SyntaxError! var can't shadow let
}

// ── React: Accidental shadowing trap ──────────
function Dashboard() {
  const [data, setData] = useState(null);

  async function load() {
    const data = await fetch(...).json();
    // ⚠️ This `data` shadows state `data`!
    setData(data);  // works but confusing
  }

  // ✅ Better: use distinct names
  async function loadBetter() {
    const freshData = await fetch(...).json();
    setData(freshData);
  }
}
★
Callback Hell
Theory

Callback Hell (aka "Pyramid of Doom") occurs when multiple async operations are nested inside each other's callbacks, creating deeply indented, hard-to-read code.

Problems: poor readability, hard error handling, difficult to reason about flow, tight coupling.

Deeply Nested Hard to Debug Poor Error Handling
✅ Solution: Promises (chaining), async/await (flat syntax), named functions instead of anonymous callbacks.
⚛React Query, SWR, and RTK Query eliminate callback hell for data fetching entirely. Understanding why they exist makes you a better consumer of these libraries.
callback-hell.js
// ── ❌ CALLBACK HELL ──────────────────────────
getUser(userId, (err, user) => {
  if (err) return handleError(err);
  getPosts(user.id, (err, posts) => {
    if (err) return handleError(err);
    getComments(posts[0].id, (err, comments) => {
      if (err) return handleError(err);
      renderAll(user, posts, comments);
      // more nesting = 🔥 pyramid of doom
    });
  });
});

// ── ✅ PROMISE CHAIN ──────────────────────────
getUser(userId)
  .then(user    => getPosts(user.id))
  .then(posts   => getComments(posts[0].id))
  .then(comments=> renderAll(comments))
  .catch(handleError);

// ── ✅✅ ASYNC/AWAIT (cleanest) ────────────────
async function loadAll(userId) {
  try {
    const user     = await getUser(userId);
    const posts    = await getPosts(user.id);
    const comments = await getComments(posts[0].id);
    renderAll(user, posts, comments);
  } catch (err) {
    handleError(err);
  }
}

  acc[u.id] = u;
  return acc;
