01

Big O notation

describes growth, not speed

Big O describes how the runtime or memory of an operation grows as the input grows — not how fast it runs on your machine. It ignores constants and focuses on the worst case, so you can compare two approaches independent of hardware.

  • O(1) — constant. Same cost no matter the input size.
  • O(log n) — logarithmic. The input is cut down each step (binary search).
  • O(n) — linear. One pass over the input.
  • O(n log n) — the cost of most good sorting algorithms.
  • O(n²) — quadratic. A loop inside a loop.
  • O(2ⁿ) — exponential. Doubles with every extra input item; avoid this.
Frontend angle — this is exactly the instinct behind “don’t call .find() inside a .map()” or “memoize this selector.” Big O is the vocabulary for why that re-render fix mattered.
complexity.js
// O(1) — constant, doesn't grow with input size
function first(arr) {
  return arr[0];
}

// O(n) — linear, one pass through the input
function sum(arr) {
  let total = 0;
  for (let i = 0; i < arr.length; i++) {
    total += arr[i];
  }
  return total;
}

// O(n²) — quadratic, nested loop over the input
function hasDuplicate(arr) {
  for (let i = 0; i < arr.length; i++) {
    for (let j = i + 1; j < arr.length; j++) {
      if (arr[i] === arr[j]) return true;
    }
  }
  return false;
}

// O(log n) — the input is halved each step
function binarySearch(sorted, target) {
  let lo = 0, hi = sorted.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (sorted[mid] === target) return mid;
    if (sorted[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}
02

Arrays

access O(1) search O(n) insert at start O(n)

Elements sit in contiguous memory, indexed from zero. That layout is what makes direct access instant — the engine just computes an offset. Anything that shifts every other element, like inserting at the front, costs a full pass.

Frontend angle — this is state in a React list, and it's why keying by array index breaks when items reorder — the index is a memory-layout detail, not an identity.
arrays.js
const arr = [10, 20, 30];

arr[1];           // O(1) — direct index access
arr.push(40);     // O(1) amortized — add to the end
arr.pop();         // O(1) — remove from the end
arr.unshift(5);    // O(n) — every element shifts right
arr.indexOf(30);   // O(n) — linear scan to find a value
03

Linked lists

insert/delete at known node O(1) access/search O(n)

Each node holds a value and a pointer to the next node — no contiguous memory required. That trade flips the array's strengths: no O(1) index access, but inserting or removing a node (once you're holding it) doesn't shift anything else. A doubly linked list adds a prev pointer too, so you can walk backwards.

Frontend angle — the DOM itself uses linked-list style pointers (nextSibling, previousSibling), and it's the shape behind an LRU cache or an undo/redo history.
linked-list.js
class ListNode {
  constructor(value) {
    this.value = value;
    this.next = null;
  }
}

class LinkedList {
  constructor() {
    this.head = null;
  }

  append(value) {                // O(n) without a tail pointer
    const node = new ListNode(value);
    if (!this.head) {
      this.head = node;
      return;
    }
    let current = this.head;
    while (current.next) {
      current = current.next;
    }
    current.next = node;
  }

  toArray() {                    // O(n)
    const values = [];
    let current = this.head;
    while (current) {
      values.push(current.value);
      current = current.next;
    }
    return values;
  }
}

const list = new LinkedList();
list.append(1);
list.append(2);
list.append(3);
list.toArray(); // [1, 2, 3]
04

Stacks

push / pop / peek O(1)

LIFO — last in, first out. You only ever add or remove from the top. It's the structure behind the call stack itself, undo history, and matching up nested pairs like brackets or tags.

Frontend angle — the JS call stack that gives you stack traces, and modal/route history where “back” pops the last thing pushed.
stack.js
// classic use: check that brackets are balanced
function isBalanced(str) {
  const stack = [];
  const pairs = { ')': '(', ']': '[', '}': '{' };

  for (const char of str) {
    if (char === '(' || char === '[' || char === '{') {
      stack.push(char);
    } else if (char in pairs) {
      if (stack.pop() !== pairs[char]) return false;
    }
  }
  return stack.length === 0;
}

isBalanced('{[()]}'); // true
isBalanced('{[(])}'); // false
05

Queues

enqueue O(1) dequeue O(n) on an array

FIFO — first in, first out. Add at the back, remove from the front. Note that Array.shift() is actually O(n) because every remaining item shifts down one slot — for a true O(1) dequeue you'd back it with a linked list or a moving start index instead.

Frontend angle — a task queue for rate-limited API calls, or the order events get flushed in an event loop.
queue.js
class Queue {
  constructor() {
    this.items = [];
  }
  enqueue(value) { this.items.push(value); }  // O(1)
  dequeue() { return this.items.shift(); }     // O(n) — array shifts
  peek() { return this.items[0]; }
}

const queue = new Queue();
queue.enqueue('a');
queue.enqueue('b');
queue.dequeue(); // 'a'

Hash maps

get / set / delete O(1) average

A key-value store where the key is hashed to compute where the value lives, giving average O(1) lookup. This is the single highest-leverage trick in interview DSA: swapping a nested loop for one pass plus a map turns O(n²) into O(n). In JS, reach for Map (any key type, ordered) or a plain object (string/symbol keys).

Frontend angle — memoizing selectors, deduping props by id, building lookup tables instead of calling .find() in a loop.
two-sum.js
function twoSum(nums, target) {
  const seen = new Map(); // value -> index

  for (let i = 0; i < nums.length; i++) {
    const complement = target - nums[i];
    if (seen.has(complement)) {
      return [seen.get(complement), i];
    }
    seen.set(nums[i], i);
  }
  return [];
}

twoSum([2, 7, 11, 15], 9); // [0, 1] — O(n) instead of O(n²)
07

Recursion

uses the call stack — watch depth

A function that calls itself on a smaller version of the problem, until it hits a base case that stops it. Every call sits on the call stack until it returns, so recursion trades explicit loops for implicit stack usage — powerful for tree- and graph-shaped problems, riskier for very deep or very large inputs.

Frontend angle — this is how you'd walk a nested comments tree, a JSON schema, or React's own element tree during reconciliation.
recursion.js
function factorial(n) {
  if (n <= 1) return 1;         // base case
  return n * factorial(n - 1);  // recursive case
}

factorial(5); // 120
08

Trees

balanced BST search O(log n) worst case O(n) if unbalanced

A hierarchical structure: one root, each node with child nodes, no cycles. A binary search tree (BST) keeps every left child smaller and every right child larger, which is what makes search fast. The three depth-first walks are preorder (node, left, right), inorder (left, node, right — visits a BST in sorted order), and postorder (left, right, node); a level-order walk (breadth-first) visits row by row using a queue.

Frontend angle — the DOM is a tree, React's fiber tree is a tree, and any nested menu, file explorer, or org chart in your UI is one too.
bst.js
class TreeNode {
  constructor(value) {
    this.value = value;
    this.left = null;
    this.right = null;
  }
}

function insert(root, value) {
  if (!root) return new TreeNode(value);
  if (value < root.value) root.left = insert(root.left, value);
  else root.right = insert(root.right, value);
  return root;
}

function inorder(root, result = []) {
  if (!root) return result;
  inorder(root.left, result);
  result.push(root.value);
  inorder(root.right, result);
  return result;
}

let root = null;
[5, 3, 8, 1, 4].forEach(n => { root = insert(root, n); });
inorder(root); // [1, 3, 4, 5, 8] — sorted, because it's a BST

Heaps

peek min/max O(1) real insert/pop O(log n)

A heap is a tree, usually stored as a flat array, that only guarantees one thing: in a min-heap, every parent is smaller than its children (the reverse for a max-heap) — so the smallest item is always at the root. That's what makes it the engine behind a priority queue. JS has no built-in heap; a real implementation sifts the new item up or down the array in O(log n). The version below trades that for clarity by re-sorting on every push.

Frontend angle — a "load the nearest N items first" queue, task schedulers, or picking the top-k results from a search without sorting the whole list.
min-heap.js
// simplified for clarity — sorts on every push (O(n log n) per insert).
// a real heap sifts the new item up/down the array in O(log n) instead.
class MinHeap {
  constructor() { this.items = []; }

  push(value) {
    this.items.push(value);
    this.items.sort((a, b) => a - b);
  }

  pop() {
    return this.items.shift(); // smallest is always at the front
  }
}

const heap = new MinHeap();
[5, 1, 4, 2].forEach(n => heap.push(n));
heap.pop(); // 1

Graphs

BFS / DFS traversal O(V + E)

Nodes (vertices) connected by edges, which may be directed or undirected, weighted or not. A tree is really just a graph with no cycles. The two core traversals are BFS (breadth-first, using a queue — explores neighbor by neighbor, finds the shortest path in an unweighted graph) and DFS (depth-first, using a stack or recursion — follows one path as deep as it goes before backtracking).

Frontend angle — a component dependency graph, a routing/state machine, or the "who follows whom" shape of a social feed.
bfs.js
const graph = {
  A: ['B', 'C'],
  B: ['A', 'D'],
  C: ['A', 'D'],
  D: ['B', 'C'],
};

function bfs(graph, start) {
  const visited = new Set([start]);
  const queue = [start];
  const order = [];

  while (queue.length) {
    const node = queue.shift();
    order.push(node);
    for (const neighbor of graph[node]) {
      if (!visited.has(neighbor)) {
        visited.add(neighbor);
        queue.push(neighbor);
      }
    }
  }
  return order;
}

bfs(graph, 'A'); // ['A', 'B', 'C', 'D']

Sorting algorithms

bubble / insertion O(n²) merge / quick O(n log n)

Bubble sort repeatedly swaps adjacent out-of-order pairs. Insertion sort builds up a sorted section one item at a time — fast on nearly-sorted data. Both are O(n²) and mostly useful for building intuition, not production. Merge sort splits the array in half recursively, sorts each half, then merges them — reliably O(n log n), stable, but needs extra memory. Quick sort picks a pivot, partitions everything smaller/larger around it, and recurses — O(n log n) on average, in place, but O(n²) on an unlucky pivot choice.

Frontend angle — in real code you'd call arr.sort() — V8's implementation is already a tuned hybrid (Timsort-like). These matter for understanding why it's fast and what trade-off it made.
bubble-sort.js
function bubbleSort(arr) {
  for (let i = 0; i < arr.length; i++) {
    for (let j = 0; j < arr.length - i - 1; j++) {
      if (arr[j] > arr[j + 1]) {
        [arr[j], arr[j + 1]] = [arr[j + 1], arr[j]];
      }
    }
  }
  return arr;
}
insertion-sort.js
function insertionSort(arr) {
  for (let i = 1; i < arr.length; i++) {
    const current = arr[i];
    let j = i - 1;
    while (j >= 0 && arr[j] > current) {
      arr[j + 1] = arr[j];
      j--;
    }
    arr[j + 1] = current;
  }
  return arr;
}
merge-sort.js
function mergeSort(arr) {
  if (arr.length <= 1) return arr;

  const mid = arr.length >> 1;
  const left = mergeSort(arr.slice(0, mid));
  const right = mergeSort(arr.slice(mid));

  return merge(left, right);
}

function merge(left, right) {
  const result = [];
  let i = 0, j = 0;

  while (i < left.length && j < right.length) {
    result.push(left[i] <= right[j] ? left[i++] : right[j++]);
  }
  return [...result, ...left.slice(i), ...right.slice(j)];
}
quick-sort.js
function quickSort(arr) {
  if (arr.length <= 1) return arr;

  const [pivot, ...rest] = arr;
  const left = rest.filter(n => n < pivot);
  const right = rest.filter(n => n >= pivot);

  return [...quickSort(left), pivot, ...quickSort(right)];
}

Searching

linear O(n) binary O(log n), needs sorted input

Linear search checks every item in order — works on anything, costs O(n). Binary search only works on sorted data, but repeatedly halves the search space by comparing against the middle element, landing at O(log n) — that's the difference between checking a million items one by one versus about twenty comparisons.

binary-search.js
function binarySearch(sortedArr, target) {
  let low = 0;
  let high = sortedArr.length - 1;

  while (low <= high) {
    const mid = (low + high) >> 1;
    if (sortedArr[mid] === target) return mid;
    if (sortedArr[mid] < target) low = mid + 1;
    else high = mid - 1;
  }
  return -1; // not found
}

binarySearch([1, 3, 5, 7, 9, 11], 7); // 3

Two pointers

O(n), often replaces O(n²)

A pattern rather than a data structure: walk two indices through the same array — often from opposite ends, sometimes both from the start — and move them based on a condition, instead of checking every pair. It's the go-to move whenever a nested loop over one array feels wasteful.

two-pointers.js
function hasPairWithSum(sortedArr, target) {
  let left = 0;
  let right = sortedArr.length - 1;

  while (left < right) {
    const sum = sortedArr[left] + sortedArr[right];
    if (sum === target) return true;
    if (sum < target) left++;
    else right--;
  }
  return false;
}

hasPairWithSum([1, 2, 4, 7, 11], 15); // true (4 + 11)

Sliding window

O(n), often replaces O(n·k)

Keep a "window" of elements — a contiguous slice of the array — and slide it forward one step at a time, updating a running result instead of recomputing it from scratch. Useful for anything about a subarray or substring: max/min sum of size k, longest substring without repeats, and similar.

sliding-window.js
function maxSubarraySum(arr, k) {
  let windowSum = 0;
  for (let i = 0; i < k; i++) windowSum += arr[i];

  let maxSum = windowSum;
  for (let i = k; i < arr.length; i++) {
    windowSum += arr[i] - arr[i - k]; // slide: add new, drop old
    maxSum = Math.max(maxSum, windowSum);
  }
  return maxSum;
}

maxSubarraySum([2, 1, 5, 1, 3, 2], 3); // 9 — from [5, 1, 3]

Dynamic programming

turns exponential into linear

DP applies when a problem has overlapping subproblems (you'd recompute the same thing many times) and optimal substructure (the answer builds from smaller answers). Memoization is top-down: recurse normally, but cache each result the first time you compute it. Tabulation is bottom-up: build the answer iteratively from the smallest case upward, no recursion at all.

Frontend angle — this is the same idea as useMemo or a memoized selector — don't redo an expensive computation you already have the answer to.
dp.js
// top-down — memoization
function fib(n, memo = {}) {
  if (n <= 1) return n;
  if (memo[n]) return memo[n];
  memo[n] = fib(n - 1, memo) + fib(n - 2, memo);
  return memo[n];
}

// bottom-up — tabulation
function climbStairs(n) {
  const ways = [1, 1]; // ways[0] = 1 (empty), ways[1] = 1
  for (let i = 2; i <= n; i++) {
    ways[i] = ways[i - 1] + ways[i - 2];
  }
  return ways[n];
}

climbStairs(5); // 8
