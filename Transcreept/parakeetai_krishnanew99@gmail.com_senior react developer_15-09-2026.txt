💬 **Question**: What is hoisting in JavaScript?

---

⭐️ **Answer**: **Hoisting** is JavaScript’s behavior of processing declarations before executing the code, so declarations appear to be available earlier in their scope. However, the behavior differs between `var`, `let`, `const`, and function declarations.

- **Function declarations** are fully hoisted, so they can be called before they appear in the source code:

```js
sayHello();

function sayHello() {
  console.log("Hello");
}
```

- A variable declared with **`var`** is hoisted and initialized with `undefined`:

```js
console.log(value); // undefined
var value = 10;
```

Conceptually, JavaScript treats it similar to:

```js
var value;
console.log(value);
value = 10;
```

- **`let` and `const`** are also hoisted in the sense that their bindings are created when the scope is initialized, but they remain in the **temporal dead zone** until execution reaches their declaration. Accessing them earlier throws a `ReferenceError`:

```js
console.log(value); // ReferenceError
let value = 10;
```

So, hoisting does not literally move code upward. It describes how the JavaScript engine creates bindings during the creation phase before the execution phase. In practice, I avoid relying on hoisting and declare variables before using them.

💬 **Question**: What is a `MutationObserver`?

---

⭐️ **Answer**: A **`MutationObserver`** is a browser API used to asynchronously observe changes in the DOM, such as adding or removing nodes, changing attributes, or modifying text content.

- I create an observer with a callback, then start observing a DOM node using `observe()` and a configuration object.
- The callback receives a list of mutation records describing what changed.
- Its callback runs asynchronously as a **microtask**, after the current synchronous JavaScript finishes and before timer callbacks such as `setTimeout`.
- This makes it useful for reacting to DOM changes without continuously polling with `setInterval`.
- I can stop observing with `disconnect()`, and use `takeRecords()` to retrieve pending mutation records.

```js
const target = document.querySelector("#app");

const observer = new MutationObserver((mutations) => {
  for (const mutation of mutations) {
    console.log(mutation.type, mutation.target);
  }
});

observer.observe(target, {
  childList: true,
  attributes: true,
  characterData: true,
  subtree: true,
});

// Example DOM mutation
target.textContent = "Updated content";

// Stop observing when it is no longer needed
observer.disconnect();
```

I would also distinguish it from `IntersectionObserver` and `ResizeObserver`: `MutationObserver` observes DOM structure or content changes, not visibility or element dimensions.

💬 **Question**: What goes into the microtask queue and the macrotask queue?

---

⭐️ **Answer**: The **microtask queue** contains callbacks that should run immediately after the current synchronous JavaScript completes, before the browser moves to the next macrotask.

- **Microtask examples:**
  - `Promise.then`, `catch`, and `finally`
  - `queueMicrotask`
  - `MutationObserver` callbacks
  - In browsers, continuations from `async/await`, because they are promise-based

The **macrotask**, or task queue, contains larger event-loop tasks such as:

- `setTimeout` and `setInterval`
- DOM events like `click`, `input`, and `keydown`
- Network and other browser events
- Script execution and message events such as `postMessage`

The general order is:

1. Execute the current synchronous code on the call stack.
2. Drain all pending microtasks.
3. The browser may perform rendering.
4. Execute the next macrotask.
5. Repeat the process.

For example:

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

queueMicrotask(() => console.log("4"));

console.log("5");
```

The output is:

```text
1
5
3
4
2
```

The timer has a zero-millisecond delay, but it still waits until the current stack and all microtasks are completed. Also, microtasks can delay timers and rendering if they continuously schedule more microtasks, so I use them carefully.

💬 **Question**: What is debouncing?

---

⭐️ **Answer**: **Debouncing** ensures that a function runs only after a specified amount of time has passed without another call. Each new call resets the timer.

It is useful for high-frequency events such as:

- Search input, where I want to call the API only after the user stops typing
- Window resize
- Form validation
- Autosave functionality

For example, in a search box, instead of sending a request for every keystroke, I can wait 300 milliseconds after the last keystroke:

```js
function debounce(callback, delay) {
  let timer;

  return (...args) => {
    clearTimeout(timer);

    timer = setTimeout(() => {
      callback(...args);
    }, delay);
  };
}

const handleSearch = debounce((value) => {
  console.log("Calling search API for:", value);
}, 300);
```

If the user types continuously, the timer keeps resetting, so the API is called only once after typing stops. In React, I would also clean up any pending timer when the component unmounts.

The difference from **throttling** is that debouncing waits for inactivity, while throttling allows execution at most once during a fixed interval.

---

⭐️ **Answer**: **Debouncing delays execution until a specified period has passed without any new calls.** Every time the function is called again, the previous timer is cancelled and restarted. This is useful for search inputs, resizing, validation, or autosave, because it prevents expensive work from running for every event.

**🔑 Key Steps**:
- Store the active timer in a closure.
- Clear the previous timer whenever the function is called again.
- Start a new timer with the latest arguments and `this` context.
- Invoke the original function only after the delay has elapsed.
- Return a cancel method when cleanup is useful.

**💻 Code**:
```javascript
function debounce(fn, delay) {
  let timerId = null;

  const debounced = function (...args) {
    // Cancel the previously scheduled invocation
    clearTimeout(timerId);

    // Schedule the latest invocation
    timerId = setTimeout(() => {
      fn.apply(this, args);
      timerId = null;
    }, delay);
  };

  // Optional cancellation for component unmount or manual cleanup
  debounced.cancel = function () {
    clearTimeout(timerId);
    timerId = null;
  };

  return debounced;
}

// Example
const handleSearch = debounce((query) => {
  console.log("Search API called for:", query);
}, 300);

handleSearch("r");
handleSearch("re");
handleSearch("react");
// Only "react" is logged after 300ms of inactivity.
```

**💡 Explanation**:
- If calls happen within the delay, `clearTimeout` removes the previous pending execution.
- The final call remains scheduled, so only the latest arguments are used.
- `fn.apply(this, args)` preserves the calling context and arguments.
- Time complexity per call is **O(1)**, excluding the wrapped function’s work.
- Space complexity is **O(1)** for the timer and stored closure state.

```javascript
const { name: userName, country = "India" } = user;

const {
  address: { city }
} = user;

console.log(userName); // Aman

console.log(city);     // Bengaluru
```

The original object is not modified; destructuring simply reads its properties and assigns them to variables. For nested objects, it is safer to provide a default value if the property might be missing:

```javascript
const { address: { city } = {} } = user;
```
