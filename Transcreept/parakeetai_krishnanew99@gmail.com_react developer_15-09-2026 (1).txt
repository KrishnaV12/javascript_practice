**🔑 Key Steps**:

- Use `setTimeout` to schedule the callback and `clearTimeout` to reset the timer if the function is called again within the wait period.

// Basic debounce function in JavaScript
function debounce(func, wait) {
  let timeout;
  return function(...args) {
    clearTimeout(timeout);
    timeout = setTimeout(() => {
      func.apply(this, args);
    }, wait);
  };
}

💬 **Question**: Why is mutating state directly dangerous in React?

---

⭐️ **Answer**: Mutating state directly in React is dangerous because it breaks React’s state management principles and can lead to unpredictable UI behavior and bugs. Here’s why:

- **React relies on immutability**: React detects changes in state by comparing previous and new state objects. If you mutate state directly (e.g., modifying an object or array in place), React may not detect the change because the reference remains the same.
- **No re-render trigger**: Direct mutation does not trigger React’s re-render cycle, so the UI will not update to reflect the new state.
- **Leads to bugs and inconsistent UI**: Since React’s virtual DOM diffing depends on immutable updates, direct mutation can cause stale or incorrect UI rendering.
- **Breaks predictable state flow**: Immutable updates ensure that state changes are explicit and traceable, which is crucial for debugging and maintaining code.
- **Can cause issues with lifecycle methods and hooks**: React hooks like `useEffect` depend on state changes to trigger effects. Direct mutation can prevent these from running correctly.

Instead, always create new state objects or arrays when updating state, for example using spread syntax or methods like `concat`, `slice`, or `map` that return new copies.

Example:

```js
// Wrong: mutating state directly
state.items.push(newItem);
setState(state); // React may not detect change

// Correct: creating new state
setState(prevState => ({
  items: [...prevState.items, newItem]
}));
```

This approach ensures React properly detects state changes and updates the UI accordingly.

In my projects, I consistently follow immutable state updates, especially when managing complex state with Redux or React’s `useState` and `useReducer`, to maintain predictable and performant UI behavior.

- **Scripts in the `<head>`**:
  - The browser loads and executes the script before parsing the rest of the HTML body.
  - This can block the rendering of the page because the browser waits for the script to download and run before continuing.
  - It may cause slower page load times and delay the display of content to the user.
  - Useful when the script is critical for the initial page setup or needs to run before the DOM is constructed.

- **Scripts at the end of the `<body>`**:
  - The browser parses and renders the entire HTML content first.
  - The script loads and executes after the page content is available.
  - This improves perceived page load speed and user experience because the visible content appears faster.
  - Common practice for scripts that manipulate DOM elements or add interactivity after the page loads.

Additional notes:
- Using the `defer` or `async` attributes on `<script>` tags in the `<head>` can also help control script loading behavior without blocking rendering.
- In modern React apps, scripts are often bundled and loaded asynchronously to optimize performance.

💬 **Question**: What is the difference between deep copy and shallow copy?

---

⭐️ **Answer**: The difference between deep copy and shallow copy lies in how they duplicate objects, especially nested objects or references:

- **Shallow Copy**:
  - Creates a new object and copies the values of the original object's properties.
  - For primitive values (numbers, strings, booleans), the values are copied directly.
  - For reference types (objects, arrays), only the reference is copied, not the actual nested object.
  - This means changes to nested objects in the copied object will affect the original object because they share the same reference.
  - Common shallow copy methods: `Object.assign({}, obj)`, spread operator `{ ...obj }`, or array methods like `slice()`.

- **Deep Copy**:
  - Creates a new object and recursively copies all nested objects and arrays, so no references are shared.
  - Changes to any nested property in the copied object do not affect the original object.
  - Deep copying is more expensive in terms of performance compared to shallow copying.
  - Common deep copy methods: using `JSON.parse(JSON.stringify(obj))` (with limitations), or utility libraries like Lodash’s `_.cloneDeep()`.

Example:

```js
const original = { a: 1, b: { c: 2 } };

// Shallow copy
const shallowCopy = { ...original };
shallowCopy.b.c = 3;
console.log(original.b.c); // Outputs 3 — nested object shared

// Deep copy
const deepCopy = JSON.parse(JSON.stringify(original));
deepCopy.b.c = 4;
console.log(original.b.c); // Outputs 3 — original unaffected
```

In my React projects, I use deep copies when updating deeply nested state to avoid unintended mutations and ensure React detects state changes properly, especially when working with complex objects or arrays. For simpler cases, shallow copies suffice and are more performant.

---

⭐️ **Answer**: The meta viewport tag is essential for mobile because it controls how a web page is displayed and scaled on different screen sizes, especially on smartphones and tablets.

- Mobile browsers by default render pages with a virtual viewport much wider than the device screen (usually around 980px) to display desktop sites properly.
- Without the meta viewport tag, the page will be zoomed out and appear very small on mobile devices, requiring users to pinch-zoom to read content.
- The meta viewport tag tells the browser to set the viewport width to the device’s actual screen width, enabling responsive layouts to work correctly.
- It also allows control over initial zoom level, scaling, and user zooming behavior.

A typical meta viewport tag looks like this:

```html
<meta name="viewport" content="width=device-width, initial-scale=1" />
```

- `width=device-width` sets the viewport width to the device’s screen width.
- `initial-scale=1` sets the initial zoom level to 100%.

In my experience building responsive React and Next.js apps, including this tag is critical to ensure the UI adapts fluidly to mobile screens, improving usability and user experience. Without it, CSS media queries and responsive designs won’t behave as expected on mobile devices.

💬 **Question**: What is the difference between inline, inline-block, and block elements?

---

⭐️ **Answer**: The difference between inline, inline-block, and block elements lies in how they behave in the layout flow and how they handle width, height, and box model properties:

- **Block elements**:
  - Take up the full width available by default (100% width of their container).
  - Always start on a new line, stacking vertically.
  - You can set width, height, margin, and padding, and these properties affect layout as expected.
  - Examples: `<div>`, `<p>`, `<h1>`, `<section>`.
  
- **Inline elements**:
  - Take up only as much width as their content requires.
  - Do not start on a new line; they flow horizontally alongside other inline elements.
  - Width and height properties generally do not apply; margin and padding affect only horizontally (left/right), not vertically (top/bottom).
  - Examples: `<span>`, `<a>`, `<strong>`, `<em>`.

- **Inline-block elements**:
  - Behave like inline elements in that they flow horizontally and do not force a line break.
  - But behave like block elements in that you can set width, height, margin, and padding, and these properties are respected.
  - Useful for creating horizontally aligned blocks that still respect box model properties.
  - Example: `<img>` is inline-block by default.

In React or any frontend development, understanding these differences helps in structuring layouts and styling components effectively, especially when building reusable UI components or responsive designs. For example, I often use `inline-block` to align buttons or icons horizontally while controlling their size precisely.
