💬 **Question**: Designing API responses and backend restrictions to prevent unauthorized cross-role data access (e.g., a doctor accessing admin data).

---

⭐️ **Answer**: At Resolute.Ai, I designed a robust Role-Based Access Control (RBAC) and attribute-based security layer at the API gateway and middleware level to ensure data isolation, regardless of whether a user calls an endpoint directly. 

Here is how we secured the architecture:

* **Token-Based Claims (JWT):** Every incoming API request carried a signed JSON Web Token containing the user's explicit roles and permissions (e.g., `role: 'doctor'`, `permissions: ['read:patient_records']`). Roles are never trusted from the client payload; they are decoded from the verified session token on the server.
* **Middleware Authorization Guards:** Before hitting any controller logic, requests passed through server-side middleware that validated the endpoint's required permission against the user's token claims. If a doctor's token hit an `/api/admin/*` route, the server immediately rejected it with a `403 Forbidden`.
* **Row-Level and Field-Level Filtering:** Even on shared endpoints (like `/api/users`), the backend controllers dynamically filtered the response payload based on the user's role. For instance, sensitive admin metadata or system configuration fields were stripped from the database query projection or serializer before sending the JSON response back.
* **Tenant and Context Isolation:** For clinical data, the backend enforced strict scoping—validating that the requesting doctor had an active clinical relationship with the requested patient ID, preventing horizontal privilege escalation even between peers, let alone across roles.

💬 **Question**: First steps to diagnose a slow and unresponsive React dashboard.

---

⭐️ **Answer**: When faced with a slow or unresponsive React dashboard, my very first step is never to start randomly rewriting code or adding memoization. Instead, I follow a data-driven diagnostic approach using profiling tools to find the exact bottleneck:

* **React Profiler & Flamegraph:** I start by wrapping the dashboard or specific suspect components with the React Profiler to record a user interaction (like typing in a filter or clicking a tab). This reveals which components are re-rendering unnecessarily, how long each render took, and what triggered the re-render.
* **Chrome DevTools Performance Tab:** For overall UI responsiveness and main-thread blocking, I record a performance profile in Chrome DevTools. I look for long tasks (taking over 50ms), excessive layout thrashing, or JavaScript execution bottlenecks that cause dropped frames.
* **Network & API Payload Audit:** I check the Network tab using TanStack Query or browser tools to inspect heavy payloads, waterfall requests, or missing pagination that might be choking the JavaScript thread when parsing large datasets.
* **Memory Leak & Heap Snapshot:** If the app gets progressively slower over time, I take heap snapshots to check for detached DOM nodes or uncleared event listeners / subscriptions that are bloating memory.

Once I have concrete metrics from the profiler identifying the culprit—whether it's an unoptimized large list, cascading re-renders from global state, or heavy computations—I target that specific component with virtualization (like React Window), code-splitting, or `useMemo`/`useCallback` optimizations.

💬 **Question**: How do you decide which parts of a React dashboard should be virtualized?

---

⭐️ **Answer**: I decide whether to virtualize a component based on a mix of DOM node count, data volume, and actual performance metrics rather than applying it blindly. 

* **DOM Node Threshold:** If a table, list, or dropdown is rendering hundreds or thousands of DOM nodes at once (e.g., a clinical patient roster with 500+ rows or a large transaction ledger), the sheer weight of the DOM tree will noticeably degrade scroll performance and memory consumption. That’s my primary trigger for virtualization using tools like `React Window` or TanStack Virtual.
* **Component Complexity per Row:** If the items in the list are simple text strings, the browser can handle a few hundred without issue. However, if each row contains complex components—like custom badges, dropdowns, interactive action buttons, or nested sub-grids—even a list of 50 to 100 items can cause jank during scrolling. In those cases, virtualizing the rendering window so only visible items exist in the DOM drastically improves FPS.
* **Static vs. Dynamic Heights:** I also evaluate whether the rows have a fixed, predictable height or dynamic heights. Fixed heights make virtualization straightforward and lightweight. If heights are dynamic (like expandable accordion rows), I ensure the virtualization library can measure and cache row heights dynamically without causing layout thrashing.
* **Performance Profiling Validation:** Before deciding, I use the React Profiler. If scroll events or filtering trigger long render passes (>16ms per frame) due to large list size, virtualization becomes the clear architectural choice. For smaller lists or paginated tables where only 10-20 items render at a time, standard pagination or infinite scroll is usually sufficient without needing virtualization overhead.

💬 **Question**: How do you handle sorting and filtering when virtualizing large tables in React?

---

⭐️ **Answer**: When dealing with massive datasets, handling sorting and filtering efficiently requires a combination of server-side data fetching and proper virtualization strategies. 

* **Server-Side Processing:** For truly large datasets (e.g., thousands of clinical records or transactions), I never sort or filter the entire dataset on the client. I offload sorting, filtering, and pagination to the backend API. When a user applies a filter or changes the sort order, we trigger a new fetch (using TanStack Query) passing those parameters, which keeps the payload size manageable and prevents browser thread blocking.
* **Client-Side Indexing / Windowing Alignment:** When virtualizing a sorted or filtered subset, the virtualization library (like `React Window` or TanStack Virtual) only renders the items currently in the visible viewport. Because the rendered indices change dynamically during scrolling, we ensure that the virtualizer is bound to the *filtered and sorted array* returned by the server or state store, not the raw unmasked dataset.
* **Preserving Scroll Position on Update:** A common UX pitfall when filtering or sorting a virtualized table is that the scroll position jumps or stays locked out of bounds. I handle this by resetting or adjusting the scroll offset of the virtualized container back to the top whenever the active filters or sort parameters change.
* **Debounced Inputs for Filtering:** For text-based search filters that trigger API calls or heavy client-side filtering, I always implement a debounce (typically 300ms) on the input change handler. This prevents excessive re-renders and redundant network requests while the user is actively typing.
